# Секреты и их смена

Все секреты production лежат в `/srv/gidravlika25/.env.production` (права `600`, в git не попадает). Меняйте секрет **сразу**, если он мог утечь (попал в чат, скриншот, чужие руки, уволился человек с доступом к серверу), и планово — раз в год.

Новые значения: `openssl rand -base64 48`; для паролей ролей БД — `openssl rand -hex 32` (только буквы, цифры, `_` и `-`). Все значения должны быть разными.

Ниже `dc` — сокращение из [runbooks.md](runbooks.md).

| Секрет | Для чего | Что будет при смене | Как сменить |
|---|---|---|---|
| `DB_RUNTIME_PASSWORD`, `DB_MIGRATOR_PASSWORD` | роли API и миграций в PostgreSQL | ничего заметного: роли получают новый пароль при deploy, API перезапускается | поменять в `.env.production`, `./deploy/scripts/deploy.sh` |
| `POSTGRES_PASSWORD` | суперпользователь PostgreSQL; им пользуются создание ролей и бэкапы | если поменять только в файле — перестанут работать deploy и бэкапы: пароль в самой базе задаётся один раз при её создании | см. ниже |
| `TOTP_ENCRYPTION_KEY` | шифрует ключи приложений-аутентификаторов в базе | **все сотрудники не смогут войти**, даже резервными кодами: старые ключи 2FA не расшифровать | только при утечке, см. ниже |
| `BOOTSTRAP_SECRET` | создание первого администратора на пустой базе | ничего — после первого администратора не используется | поменять, `deploy.sh` |
| `ALTCHA_HMAC_SECRET` | подпись антиспам-задач форм сайта | формы, открытые в момент смены, один раз автоматически решают задачу заново | поменять, `deploy.sh` |
| `CATALOG_REVALIDATION_SECRET` | API сообщает сайту, что каталог изменился | на время deploy правки каталога видны на сайте с задержкой до минуты | поменять, `deploy.sh` (пересобирает сайт) |
| `OPS_STATUS_TOKEN` | доступ монитора к `/ops/status` | пока значения в сервере и в GitHub различаются, монитор присылает alert | поменять в `.env.production` и в GitHub → Settings → Secrets → Actions, затем `deploy.sh` |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | хранилище фото | ничего, если новый ключ создан до отзыва старого | создать ключ у провайдера → записать → `deploy.sh` → проверить загрузку фото → отозвать старый |
| `BACKUP_S3_*` | внешняя копия бэкапов (если включена) | при ошибке deploy остановится: отправка бэкапа обязательна | так же, как S3: новый ключ → запись → `deploy.sh` → отзыв старого |
| `BACKUP_AGE_RECIPIENT` | публичный ключ шифрования внешней копии | новые бэкапы шифруются новым ключом | **сохраните старый закрытый ключ**: без него не расшифровать прежние бэкапы |
| `DADATA_API_KEY` | подсказки адресов | до `deploy.sh` подсказки не работают (адрес вводится вручную) | новый ключ в кабинете DaData → запись → `deploy.sh` |
| `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` | карта на странице контактов; ключ публичный, ограничен по домену в кабинете Яндекса | — | поменять, `deploy.sh` (значение встраивается в сборку) |

Кроме файла на сервере: SSH-ключ доступа к серверу (раздел про SSH в [Развертывание.md](../Развертывание.md)), пароли сотрудников (меняются в Back Office → «Пользователи»), секрет `OPS_STATUS_TOKEN` в GitHub.

## Пароль суперпользователя PostgreSQL

Сначала база, потом файл — иначе deploy и бэкапы потеряют доступ:

```bash
dc exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\password"'
```

psql дважды спросит новый пароль и не покажет его. Затем запишите тот же пароль в `POSTGRES_PASSWORD` в `.env.production` и выполните `./deploy/scripts/deploy.sh`.

## Ключ шифрования 2FA

Меняйте, только если он утёк: после смены каждый сотрудник заново подключает приложение-аутентификатор и получает новые резервные коды.

1. Запишите новый `TOTP_ENCRYPTION_KEY` в `.env.production` и выполните `./deploy/scripts/deploy.sh`.
2. Сбросьте 2FA всем (то же, что кнопка «Сбросить 2FA» у каждого пользователя):

   ```bash
   dc exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
   BEGIN;
   UPDATE "User" SET "twoFactorSecret" = NULL, "twoFactorEnabled" = false,
                     "twoFactorEnabledAt" = NULL, "lastTotpCounter" = NULL;
   DELETE FROM "AuthSession";
   DELETE FROM "AuthRecoveryCode";
   DELETE FROM "AuthTwoFactorChallenge";
   COMMIT;
   SQL
   ```

3. Сообщите сотрудникам: при следующем входе после пароля появится QR-код.
